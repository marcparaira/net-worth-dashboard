# Net Worth Dashboard
**Backend Language Study: Python vs Rust**

**Version:** 0.1
**Status:** Draft

## 1. Scope

Select the language and framework for the backend API: authentication,
create/read/update/delete endpoints for financial data, the analytics
(`ledger`, `timeseries`, `dashboard`, `rebalancing`), and the import/export
commands.

Out of scope: the frontend (React/TypeScript), the database (PostgreSQL, see
[storage-study.md](storage-study.md)), and infrastructure code (AWS CDK).

**Starting point:** a working Python/FastAPI prototype with Pydantic models,
analytics, and unit tests.

**Workload:** small and mostly idle. Each request touches at most a few
thousand values per user; the work is input/output-bound (database and
network), not CPU-bound.

## 3. Options Considered

| Option | Stack |
|---|---|
| A. Python | FastAPI, Pydantic, SQLAlchemy, Alembic, `decimal.Decimal`, pytest, Ruff, basedpyright |
| B. Rust | Axum, Tokio, serde, sqlx (with its migrations), `rust_decimal`, utoipa (OpenAPI), cargo test, Clippy |
| C. Python with Rust extensions | Option A, with CPU-heavy functions written in Rust and called through PyO3/maturin |

## 4. Analysis

✔ meets · ◐ partially meets · ✘ does not meet

| Req. | A. Python | B. Rust | C. Python + Rust extensions |
|---|---|---|---|
| LR-01 Reuse | ✔ Existing code and tests carried over | ✘ Full rewrite of analytics and tests | ✔ Same as A |
| LR-02 Delivery speed | ✔ FastAPI and Pydantic minimize boilerplate for CRUD and validation | ◐ More code and slower compilation for the same endpoints | ◐ As A, plus a second build toolchain |
| LR-03 Exact money and type safety | ◐ `Decimal` is exact; type errors caught by basedpyright and Pydantic, not by a compiler | ✔ `rust_decimal`; the compiler catches type and null errors | ◐ Same as A |
| LR-04 Ecosystem | ✔ All needed libraries are mature; OpenAPI generated by FastAPI | ◐ Available, but younger; OpenAPI needs annotations; no Alembic equivalent with autogeneration | ✔ Same as A |
| LR-05 Performance | ✔ Well within two seconds for this data size | ✔ Faster, but the difference is not noticeable here | ✔ |
| LR-06 Hosting cost | ◐ ~60–100 MB memory per process; slower cold start | ✔ ~10–20 MB memory; near-instant start | ◐ Same as A |
| LR-07 Image size | ◐ ~60–100 MB on Alpine | ✔ ~10–20 MB static binary on a minimal image | ◐ Same as A, plus a build stage for Rust |
| LR-08 Security | ◐ Memory-safe; larger runtime and dependency surface | ✔ Memory-safe; smaller runtime surface | ◐ Same as A |
| LR-09 Maintainability | ✔ Familiar, widely known | ◐ Steeper learning curve for contributors | ✘ Two languages for a small codebase |

**Notes on cost (LR-06).** Rust's lower memory use does not reduce the bill at
this scale: the smallest Fargate and App Runner sizes (0.25 vCPU, 0.5 GB) fit a
Python process comfortably. Faster cold starts would matter only on AWS Lambda,
and even there the database's resume delay after a pause (about 15 seconds) is
far longer than either language's start time.

**Summary:**

- **A** reuses the prototype, has the most direct path through the roadmap, and meets the performance goal with margin. Its weaknesses (memory, image size, runtime type checking) have little practical effect at this scale.
- **B** is technically stronger on safety, footprint, and speed, but the advantages do not translate into lower cost or a better experience for this workload, and it requires rewriting working code.
- **C** solves a CPU-bound problem the application does not have, at the cost of two toolchains.

## 5. Final Decision

**Python**, with FastAPI, Pydantic, SQLAlchemy, and Alembic.

To narrow the gap with Rust on correctness:

- Replace `float` with `decimal.Decimal` for all amounts, in models, analytics, and API schemas.
- Run basedpyright in strict mode and Ruff in CI, failing the build on errors.
- Keep the analytics as pure functions over typed models, so they stay easy to test and, if ever needed, to port.

**Revisit** if the backend gains CPU-heavy features (for example, Monte Carlo
retirement projections over many scenarios); start with option C for the
specific hot path rather than a full rewrite.
